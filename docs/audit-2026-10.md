## Summary of findings (before this round)

The site is in better shape than the brief's "known earlier" list: the
NorthGrid brand, the stock photos, the github.io share tags, the gradient hero
text, the three orbs and the white-at-52% muted text have already gone. What is
left, in order of weight:

1. **The page has no security headers at all.** API responses carry Helmet's set
   (plus `access-control-allow-origin: *`); every HTML, JS and CSS response has
   none. Fix is an Nginx change, which a push does not deploy.
2. **Postgres listens on every interface** with `postgres`/`postgres`, and Docker's
   published ports bypass UFW, so it is reachable from the home network.
3. **Cloudflare injects Web Analytics** (`static.cloudflareinsights.com`) into the
   HTML for browsers. Nobody added it in code. It is the only third-party request
   the page makes.
4. **The old Jekyll site is still published** at
   `https://manugahewa.github.io/portfolio-v2/` by
   `.github/workflows/jekyll-gh-pages.yml`. It renders the stale README, has a
   canonical pointing at itself, and serves `portfolio_projects.txt` (the working
   notes, `[VERIFY]` markers included) to anyone.
5. **Crawlers get an empty page.** The HTML body is `<div id="root"></div>`, the
   `<h1>` is a tagline that does not contain your name, and `robots.txt`,
   `sitemap.xml` and every unknown URL return the SPA shell with a 200.
6. **No rate limit, no bot protection, no retention** on the contact form, and the
   error handler would write a visitor's name, email and message into the system
   journal if an insert ever failed validation.
7. **Several claims contradict the page they sit on**, the strongest being
   "Every claim on this page is backed by code you can open" next to eight
   projects with no public repository. Full list in appendix B, for you to mark.
8. **Three serious axe failures**, all from one pattern: project cards are
   `<article role="button">` with links inside them. Contrast is close to clean:
   four small elements fail AA.
9. **The deploy does not run the seed**, so copy changes in `backend/prisma/seed.ts`
   never reach production on a push. Any claims you reword would silently not
   deploy.

### Prerendering: options and trade-offs

The HTML body today is `<div id="root"></div>`. Google renders JavaScript, usually
with a delay; most other crawlers, link-preview scrapers and AI crawlers do not,
so they see a page with no name in the body and no projects.

| Option | What it is | For | Against |
|---|---|---|---|
| A. Leave it | Rely on Google's renderer. | Zero work. | Fails the definition of done; every other consumer sees nothing. |
| B. Hand-written fallback | Static summary inside `#root`, replaced when React mounts. | No build change. | Content duplicated by hand and drifts; visible flash when React replaces it. |
| C. Build-time prerender, no framework | After `vite build`, render the existing React tree with `react-dom/server`, write it into `dist/index.html` and `dist/privacy/index.html`, hydrate on the client. Project summaries come from a shared content module that the seed also reads; the deploy runs the seed, so the API and the HTML agree, and a CI test checks the API's output against the module. | Keeps Vite and every component; no new runtime dependency; HTML contains name, intro, all project titles, summaries and outcomes, skills and contact details; the site still works, cards included, if the API is down. | About 150 lines plus small SSR-safety fixes (layout effects, media-query initial state). The frontend build now imports a file from outside `frontend/`. Case-study details still load from the API when a card opens, so they are not in the HTML. |
| D. A framework | vite-plugin-ssg, Vike, Astro, or Next.js. | Real routing and per-page data; easy to give each case study its own URL later. | A migration for a one-page site; Next.js would replace Vite outright; every component re-checked against a new runtime. |

**Recommendation: C.** It is not a framework, and its commit stands alone, so it
can be reverted cleanly. If you later want each case study on its own URL
(`/work/dms`) so the full text is indexed, that is the point where D starts to
pay for itself; it belongs with the Phase 4 layout decision.

**Status: done (`ab8c7d7`), option C.** Without JavaScript the home page now
holds about 13,400 characters of text (before: none), with the name as the
only `<h1>`, every project title, summary and outcome, the skills, and the

### Two directions

**Direction A: Plain dark, one accent.**
*Palette:* warm near-black ground (around #121110), off-white text, one muted
grey for secondary text, ember (#e98e49) only for links and the primary action;
sky blue and the seven category colours go. *Type:* IBM Plex Sans for text and
IBM Plex Mono for the few code labels, both SIL Open Font License, self-hosted.
*Layout:* a single reading column about 70 characters wide. Each project is a
full-width case-study row: screenshot left, what you built, for whom, with what,
and what happened on the right; no card grid. Skills become a short grouped list
with "used in" links instead of a radar and counts. Contact is the form and
three links. *3D scene:* only the hero gyroscope survives, in one canvas that
pauses off screen, swapped for a still render on reduced motion or weak devices;
the five other scenes (starfield, field, corridor, globe, signal) are removed.

**Direction B: Light technical paper.**
*Palette:* warm off-white paper (around #f5f3ee), ink text (#1c1c1a), hairline
rules, one deep accent (rust or ink blue); no gradients. *Type:* Source Serif 4
for headings, Source Sans 3 for text, JetBrains Mono for code, all Open Font
License, self-hosted; serif as the system, not as italic accents. *Layout:* a
document with a slim left table of contents on desktop (Work, Skills, Contact).
Case studies read like short write-ups: Problem, What I built, Result, Links,
with numbered figures for screenshots. *3D scene:* the gyroscope becomes
"Figure 1", drawn as dark line art on paper inside a bordered figure with a
caption ("rendered live with Three.js; still image on reduced motion"); no
other scenes.

Both keep the engineering in the 3D work and make it degrade to a still image;
both remove the reveal-on-scroll, spotlight and hover gimmicks. A suits the
current site's mood; B is the larger change and the more distinctive one.

**Screenshot slots** (either direction): files in `frontend/public/work/<slug>/`,
named `<slug>-1.webp`, `<slug>-2.webp`... (1600px wide, under 200 kB each), with
alt text and captions written next to the data. RxFlow is `exercise`, DMS is `dms`.
