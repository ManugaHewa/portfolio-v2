1. RxFlow - HAND THERAPY CANADA EXERCISE PRESCRIPTION APP
==========================================================================
Tagline:   A cross-platform rehab app that lets hand therapists prescribe
           exercise programs and lets patients follow, track and understand
           them from their phone.
Category:  Mobile / Full-stack / Cloud
Context:   SE4450 Software Design II capstone, Western University (Team 5)
Client:    Hand Therapy Canada (real industry sponsor)
Role:      Team Lead and Full-stack Developer
Dates:     September 2024 - April 2025 [VERIFY]
Team size: 5 [VERIFY]
Status:    Completed

Tech stack
- Frontend: React Native, TypeScript, Expo Router, React Native Web
- Backend: Node.js, Express [VERIFY Express], REST API
- Database: MongoDB Atlas
- Cloud / DevOps: Docker, Google Cloud Run, Google Compute Engine
  (Ubuntu 22.04, e2-small), Google Secret Manager, HTTPS load balancing,
  DuckDNS
- APIs: Google Cloud Speech-to-Text (LINEAR16, 16 kHz), translation service
- Testing: Jest [VERIFY], roughly 80% coverage on critical paths [VERIFY]

The problem
Hand Therapy Canada treats hand, wrist, elbow and shoulder injuries across
Southwestern Ontario. Home exercise programs were being shared as videos
saved to a patient's camera roll and paper handouts. Therapists had no
reliable way to know whether patients were actually doing their exercises,
patients lost or confused their videos, and there was no support for
patients who spoke other languages or for younger patients.

What I built
RxFlow is a React Native app that runs on iOS, Android and the web from one
TypeScript codebase. It has two sides:

- Clinician portal: therapists assign exercise programs to patients, pick
  from a central video library, set schedules, and review each patient's
  completion history.
- Patient app: patients see today's exercises, watch the demonstration
  video, check off completed sets, and see a weekly progress bar. Reminders
  nudge them when a session is due.

Key features
- Centralized exercise video library served from the backend instead of
  patients' camera rolls
- Weekly completion tracking with a visual progress bar
- Scheduled exercise reminders
- Captions on exercise videos generated with Google Speech-to-Text
- Six languages: English, French, Spanish, German, Italian and Portuguese
- "Fun Mode", a child-friendly interface for younger patients
- Patient onboarding designed to take under two minutes
- Backend REST routes for /auth, /videos, /progress, /translation,
  /captions and /schedule
- Cookie-based authentication, CORS configuration and secrets stored in
  Google Secret Manager

Biggest technical challenge
For months the iOS build could not talk to the backend. iOS refuses
insecure HTTP connections by default, so the fix was not in our app code;
it was in the infrastructure. I worked through TLS certificates, HTTPS
termination, a Google Cloud load balancer and DuckDNS for the domain,
debugging each layer until the full path of iOS app -> HTTPS -> backend
worked end to end. Rather than cutting the feature to hit the deadline, I
stayed on it (including a 3 AM finish) and demonstrated the working iOS
connection to the client. Earlier I also fixed a "This screen doesn't
exist" routing bug caused by mixing Expo Router with React Navigation and
nesting two NavigationContainers.

Outcome
- Delivered a working cross-platform app to a real healthcare client
- Led a 5-person team through requirements, design, build and demo [VERIFY]
- Migrated the backend from a single Compute Engine VM to containerized
  Cloud Run deployment [VERIFY order]

What I learned
Infrastructure problems (certificates, networking, platform security rules)
can block a product as completely as a code bug, and the only way through
is reading documentation carefully and testing each layer on its own.
Leading the team also taught me to break work into pieces people could own
independently.

  frontend together

  RBAC for admin roles

- Prisma schema required Donation.type even when some flows didn't supply
  it; redesigned the field as optional and handled it in the API layer.
- An Express requireAdmin middleware resolved to undefined because of an

- Middleware that tried to reassign req.query failed (it is read-only in

- Prisma generate failed with EPERM on Windows because the query engine

  before regenerating.
- The frontend returned a 404 on port 5173 because the dev script wasn't
  launching Vite correctly; rewrote the script with concurrently.

4. FLAKY TEST DETECTOR
==========================================================================
Tagline:   A machine-learning tool that reads CI history from real
           open-source projects and predicts whether a failing test is a
           real bug or just flaky.
Category:  Machine learning / Developer tooling
Role:      Solo Developer
Dates:     August 2026 - present
Status:    Pipeline built; scaling up data collection

Tech stack
- Python, GitHub REST API (Actions runs and job logs)
- pandas, scikit-learn, XGBoost
- Target repos: apache/airflow, scrapy/scrapy
- CLI tooling, unit tests for log parsing

The problem
A "flaky" test fails randomly because of timing, network or environment
issues, not because the code is broken. Engineers waste hours
investigating these false alarms. Large projects rerun failing tests
automatically, which leaves a useful trail: a test that failed and then
passed on the same commit was almost certainly flaky.

What I built
A four-stage pipeline:
1. collect_data.py - pulls GitHub Actions run history and raw job logs
   through the API, with a --list-jobs helper to find the right test jobs.
2. features.py - labels each failure as flaky or real using the
   "failed, then passed on rerun, same commit" signal, then builds
   features such as historical failure rate, error-message similarity and
   duration z-score, using only data from before each failure so the model
   can't see the future.
3. train.py - trains logistic regression or XGBoost with a time-based
   train/test split and reports precision and recall instead of accuracy.
4. predict_cli.py - scores new failures and prints a readable flakiness
   report.

Key engineering decision
The first plan was to parse JUnit XML reports, but I found (through an
open upstream issue) that pytest's JUnit output does not reliably record
rerun attempts. Using it would have silently produced wrong labels. I
switched to parsing the raw GitHub Actions job logs, where
pytest-rerunfailures prints explicit RERUN lines. Catching a data-quality
problem before it corrupts the dataset is the kind of issue that makes or
breaks an ML system.

Current status
100 runs of a single Scrapy job produced only one usable labelled row, so
the next step is collecting 500+ runs across multiple Python-version job
variants, where environment-dependent flakiness is more likely to show up.
Planned: validate labels against the project's own flaky-test issue tags,
report precision/recall on held-out commits, and package the tool as a
GitHub Action.

7. PIX2PIX GAN WITH SELF-ATTENTION
==========================================================================
Tagline:   An image-to-image translation model that improves on Pix2Pix
           with self-attention and a multi-scale discriminator.
Category:  Deep learning / Computer vision
Context:   Academic project, AI course at Western [VERIFY: AI II]
Role:      Developer [VERIFY: solo or team]
Dates:     [VERIFY: 2024-2025]
Status:    Completed

Tech stack
- Python, PyTorch
- U-Net generator, PatchGAN discriminator
- Dataset: [VERIFY: e.g. CMP Facades or Maps from the original Pix2Pix
  paper]
- Google Colab / GPU training [VERIFY]

What I built
Pix2Pix learns to turn one kind of image into another, such as a building
layout sketch into a photo-realistic facade. A generator creates the output
image and a discriminator tries to tell real from generated, and the two
improve by competing.

- Generator: a U-Net with skip connections so fine details from the input
  survive into the output, extended with self-attention layers so the model
  can relate distant regions of the image (for example keeping windows on
  opposite sides of a building consistent).
- Discriminator: a multi-scale PatchGAN that judges realism on small
  patches at several resolutions, catching both fine texture and overall
  structure.
- Trained with the standard adversarial loss plus L1 reconstruction loss.
- Compared results against a baseline Pix2Pix [VERIFY] visually and with
  metrics such as SSIM / PSNR or FID [VERIFY which].

What I learned
How unstable GAN training can be, why architecture choices like attention
and multi-scale discrimination matter, and how to evaluate generative
models when "accuracy" doesn't apply.
